# research-doc-template

연구용 anti-AI-slop 문서 템플릿.

이 템플릿은 마이크로매니징 도구에 가깝다. auto 모드는 개발 중.

English: [README.md](README.md)

## 사람이 읽을 것

TL;DR은 제공하지 않는다. 목적은 읽는 게 좋고, 사용법은 읽어야 한다.

### 목적

AI 보조 연구에서는 사람이 검증하는 속도보다 결과물이 빨리 생산되고, 그 격차가 인지부채로 쌓인다. 이 저장소는 AI 보조 연구에서 반복된 다음 실패 사례를 막기 위해 여러 테스트를 거쳐 경험적으로 다듬은 것이다.

- 정보량 과다
- 판단의 증발 / 잘못된 지침
- 목표 정렬 부재
- 실행 허들 / 컨텍스트 비용
- 정합성 부재 / 파일 관리

#### 정보량 과다 — 인지부채의 가속

연구에 필요한 정보량보다 많은 텍스트가 쌓여 읽기가 힘들어지고 인지부채가 커진다. 실제로 필요한 양과 제공되는 양의 차이가 크고, 정보가 위계 없이 제공되어 이를 가속한다.

1. anti-slop 지침으로 slop의 절대량 감소
    - 대화 시 쓸데없는 여백 최소화
    - 필요 없는 주석, 장황한 정보 생략

2. 정보 위계 상실로 소화하기 어려운 정보
    - 가져오는 정보는 항상 요약·분류해서 읽기 편하게 제공

3. 문서화 남발
    - 문서로 정리하려 해도 문서 자체가 몇백 개 생기는 문제
    - 최종적으로 증류된 문서만 남기는 문서 생명주기 도입

4. 인지부채 숙제 (선택)
    - AI와 사용자의 문서 영역 분리
    - 사용자가 직접 유지보수하는 journal 존재
    - 사용자가 모르는 부분은 나중에 점검을 요청할 수 있음

#### 판단 증발 / 잘못된 지침

한 턴에 과다한 정보와 함께 사용자 의중을 묻는 여러 질문이 들어오고, 일부에만 답하다 보면 판단했어야 하는 문제까지 사라진다.

1. 사용자에게 요청한 판단 목록은 명시적으로 추적
    - 이 목록은 조용히 사라질 수 없음
    - 보고는 항상 요청 QUEUE 개수로 끝남

2. 암묵적 동의 금지
    - AI는 질문에 답이 없으면 암묵적 동의로 간주하는 경향이 있음
    - 판단은 명시적 발언으로만

3. 사용자의 잘못된 지침
    - 궁극 목표 A를 위해 계획 B를 세운 뒤, 사실은 관련이 적거나 더 좋은 방법을 배제한 C 방식으로 진행하라는 요구
    - 같은 요청을 AI에 시켰을 때 누구는 결과가 나오고 누구는 안 나오는 이유 — AI가 알아도 사용자 요구를 우선함
    - 실행 시 목표 정렬 검사로, 무조건 실행에 대한 작은 안전장치 확보

#### 목표 정렬 부재

의식의 흐름처럼 최신 컨텍스트에만 집중해 연구 내용이 계속 발산하는 문제.

1. 컨텍스트에 명시적 목표 부재
    - 처음 중시하던 목표가 사라지고 마지막 요청이 주 목표로 재합성됨
    - "ablation 진행" 같은 목표가 지금까지의 대화가 아니라 마지막에 언급된 세부 옵션에 강하게 의존
    - 현재 의도를 파일(intent stack)에 둔다
    - 압축 후 · 세션 시작 · 목표 주입 시 읽는다
    - intent stack으로 현재 의도의 실행 옵션 / 탐색 목록을 관리

2. 조용한 drift
    - 질문을 거듭하면 의도가 재합성 노이즈처럼 조금씩 밀려간다. 어느 것도 점프는 아닌데 도착지는 딴 곳
    - intent stack이 추적하므로 drift가 일어나면 intent unroll이 발생
    - unroll 시 환기

3. 좀비 아이템
    - 반쯤 끝난 작업이 곳곳에 남아 open loop로 잔류
    - /close 판정으로 아이템 관리

#### 실행 허들 / 컨텍스트 비용

탐색성 질문 하나에 파일이 바뀌고 몇 시간짜리 job이 걸린다. 반대로 watch를 잘못 걸거나 반복 확인하다 보면 컨텍스트 전체를 다시 태운다.

1. 폭주 실행
    - 상호작용 모드를 둘로 나눔
    - [pingpong]은 기본 — 탐색과 가벼운 문서·코드 수정만
    - [execute]는 사용자의 명시적 진입어로만 — 여기서만 스크립트가 돈다
    - "~하면 되지 않나?", "~이길 바라는데"는 트리거가 아니다
    - [pingpong]에서 명시적 트리거와 엄밀한 목표 설정을 거친 뒤 [execute]

2. KV 캐시 윈도우를 벗어나는 일을 줄이도록 관리
    - 애매한 run이 쌓이면 KV 캐시 시간을 넘어 재입력 비용 증가
    - "B안 테스트해볼래?"에 B만 돌리지 않는다. 같은 추상화 레벨의 형제 옵션을 묶어 exp 하나 · run 하나로 제안
    - 결과적으로 사용자 uptime/downtime의 조각모음 역할

#### 정합성 부재 / 파일 관리

파일이 많아지면서 정합성이 점점 어긋난다(SSOT 위반). 파일 계층구조가 없다.

1. 문서 생명주기 도입
    - inbox(아이디어) → plan → adopted/rejected. 세부 내용은 archive로
    - 실패한 아이디어를 기계적으로 나열하지 않고 아이템 기준으로 계층화해 묶어, 컨텍스트를 아끼며 접근 가능하게
    - 최종적으로 한 아이디어의 수많은 결과물을 다시 증류해 한 아이템은 한 문서로 종결 가능하게

2. 기계 검사
    - tools/lint.sh: 링크 해소 · 중복 id · plan 목록 · run ↔ exp 미러 · 스냅샷 · research 고아. /check로 필요할 때 실행
    - 조용한 세션 종료로 생긴 아이디어·문서 slop은 /check로 검사해 살리거나 폐기

3. 문서 간 SSOT
    - 복사하지 않고 링크한다. 예외는 adopted 재구성 스냅샷 하나

4. 원문 보존
    - 사용자의 말은 AI가 재서술하지 않는다
    - 요청을 정교화하는 것 이상으로, 사용자의 원본 요구를 에이전트에게 전달할 때 희석되는 위험이 있음

5. 디스크 slop
    - 죽은 실험의 산출물이 끊임없이 쌓이고, 세션 종료 시 파일 관리가 없음
    - docs에서 결과물을 추적하고, 문서 생명주기에 따라 디스크도 정리

### 사용법

산출물 위치에 대한 지침은 실험 결과 위치(runs/)만 포함하고 나머지는 일부러 두지 않았다. 

#### 도입

- 기존 저장소로의 도입은 AI에게 맡긴다 — 절차는 [README.md](README.md)의 "AI adoption procedure".
- 도입 시 CLAUDE.plugin.md의 내용이 프로젝트 root의 CLAUDE.md 에 지침으로 추가된다.
- 기존 문서는 AI가 목적지 표를 제안하고, 사용자가 판정한 뒤에만 이동한다.

#### 문서의 세 상태

```
inbox (아이디어) → plan/<item>/ (실험 축적) → adopted (채택, 승인 필수)
                                            | rejected (기각, 사인 필수)
                                            └ 원본 폴더는 archive/로 동결
```

- 아이디어는 `docs/inbox`에. 직접 넣어도 좋고, 대화로 AI와 정제해서(`/inbox`) 넣어도 된다
- 실행 단위로 올릴 때, `/register`를 통해 구체화하며 `docs/plan`으로 올린다. 해당 서브폴더에 그 아이디어의 실험들도 포함
- `/close`로 adopt 또는 reject
    - adopt하면 재현 가능한 수준으로 결과물을 증류해 보고서 작성
    - reject하면 결과물은 상대적으로 더 버려지고, 시도에 대한 기록만 증류

#### 사용자 문서 위치 분리

사용자가 실제로 쓰는 문서는 두 곳.

- `docs/inbox` — 위와 같음
- `docs/journal.md` — 사용자의 이해와 개발일지. AI는 쓰지 않고 읽는다: 세션 시작, 의도 교체(unroll), /check. 결과가 journal의 주장과 어긋나면 AI가 질문으로 알려준다. (optional)

#### 결정 사항은 Queue를 통해

- `docs/QUEUE.md` 안에 미결 사항들의 집합이 있다.
